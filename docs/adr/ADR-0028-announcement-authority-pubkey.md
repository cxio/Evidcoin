# ADR-0028: 全网通告与授权公钥更新机制

## Status（状态）

Accepted

## Context（背景）

Evidcoin 需要一种机制，允许官方或可信实体向全网节点广播通知信息（如协议升级预告、安全警告、重大公告等）。

评审报告（M-9）提出以下问题：
1. 全网通告的载体和格式？
2. 通告的可信度如何保证（防止伪造通告欺骗用户）？
3. 授权公钥本身的轮换和更新机制？

## Decision（决策）

### 通告载体

**全网通告通过普通 Proof 类型的输出项携带**，在 Proof 输出的标题（Title）字段中标注特殊前缀来与普通存证区分：

```
Title 格式：Announcement:<Level>: <通告标题>
```

- `<Level>` 为通告级别（如 `INFO`、`WARNING`、`CRITICAL`），供客户端显示时按重要程度排列。
- 通告内容放在 Proof 的正文数据字段（Body/Attachment）中。

全网通告本质上是链上的一笔普通交易，接受与普通交易相同的共识规则。区别仅在于**客户端解析层**的识别和展示。

### 授权公钥

**客户端仅向来自"授权公钥"的全网通告负责**，未授权公钥签发的通告不显示给用户，也不被第三方系统认可处理。

授权公钥规则：

- **初始授权公钥**：创世区块（`#0`）的签名公钥和 `#1` 号区块的签名公钥为原始授权公钥。
- **轮换机制**：之前的授权公钥可以签名并发布一条"公钥更新通告"，声明新的授权公钥；旧公钥在更新通告中同时声明自身是否失效（终止授权资格）。
- **公钥权威性排序**：授权公钥的权威级别由其**初始授权所在区块高度**决定，区块高度越低，权威性越高。这在授权公钥私钥泄露或通告消息冲突时，用于裁定哪一方具有更高优先级。

### 冲突与泄露处理

- 若两条通告内容冲突，客户端以发出通告的授权公钥权威级别（区块高度越低越高）为准。
- 若某个授权公钥的私钥疑似泄露，权威级别更高的授权公钥可发布一条"撤销通告"宣告其失效。

## Rationale（理由）

1. **链上存证，不可伪造**：将通告作为 Proof 输出永久记录到区块链上，通告内容一旦上链即不可篡改，具有高度可信赖性。
2. **利用现有交易基础设施**：无需为通告引入新的交易类型或额外的网络消息类型，直接复用现有的 Proof 输出，降低实现成本。
3. **信任链设计**：通过初始创世区块公钥锚定授权根，形成可追溯的信任链。这有中心化的逻辑，但合理地满足了官方通告的场景需求——授权公钥不止一个，进一步分散了中心化风险。
4. **权威性与区块高度挂钩**：越早产生的授权公钥（更低区块高度）越权威，这与区块链"历史越久、证明越可信"的基本价值观一致，也保证了在私钥泄露时历史权威方可以干预和纠正。
5. **客户端层过滤**：通告的"可信"判定发生在客户端展示层，不影响链上共识规则，保持了协议层的简洁性。

## Consequences（影响）

- 需在 `docs/proposal/13.Public-Service-Interfaces.md` 或 `docs/conception/3.公共服务.md` 相关文档中补充全网通告机制的规范描述。
- 客户端实现需支持识别 `Announcement:<Level>:` 格式前缀，并根据授权公钥列表过滤通告。
- 需定义"公钥更新通告"的正文格式（至少包含：新公钥、旧公钥是否失效的声明、发布公钥的签名）；该格式可在独立的文档章节中描述。
- 实现授权公钥权威级别排序的逻辑：持久化初始区块高度与公钥的映射关系。

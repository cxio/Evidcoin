# DEC-0014: 全网通告授权信任链

## Status（状态）

Accepted

## Context（背景）

`conception/2.共识-端点约定.md` 已明确全网通告是唯一中心化机制，以 Proof 输出发布，标题前置 `Announcement:<Level>:`，签名者由官方 App 内置或授权链上的授权公钥。它没有固定授权公钥如何初始化、轮换和撤销，也没有给出授权根公钥本身的升级路径。

这些授权规则只服务于客户端展示层：未被授权公钥签署的通告仍是普通链上数据，不因此影响区块、交易或 Proof 的链上合法性。

## Decision（决策）

全网通告授权采用客户端展示层信任链，不影响链上共识。

初始锚点：

- 创世区块 `#0` 和 `#1` 区块的签名公钥是初始授权根集合。
- 已授权公钥可发布公钥更新通告，声明新增授权公钥。
- 已授权公钥可发布撤销通告，声明某个授权公钥失效。
- 未被授权公钥签署的 `Announcement:<Level>:` Proof 仍是普通链上数据，但客户端不应按官方全网通告展示。

授权根演化：

- 任意时刻存在一个当前授权根集合 `R = { rootKey_i }`，初始为创世 `#0` 与 `#1` 区块的签名公钥。
- 根集合的演化通过特定标题的 Proof 通告完成：

| 操作 | 通告标题 | 内容 |
|------|----------|------|
| 新增根 | `Announcement:Root:Add:` | 携带新增公钥及其简要说明。 |
| 撤销根 | `Announcement:Root:Revoke:` | 携带被撤销公钥指纹。 |
| 轮换根 | `Announcement:Root:Rotate:` | 等价于一次原子的“新增 + 撤销”。 |

- 演化通告必须由当前根集合中至少 `ceil(|R| / 2) + 1` 个不同根公钥的多签共同签发；当 `|R| = 1` 时退化为单签，但应在通告中同步追加至少一个新根，避免单点永存。
- 撤销通告生效后，被撤销公钥不再出现在 `R` 中；其历史签发的通告本身仍然有效，仅授权事实变更，不追溯历史。
- 客户端按时间顺序回放所有 Root 演化通告以重建当前 `R`，并以此判定后续 `Announcement:<Level>:` 通告是否可被作为官方通告展示。

授权冲突按授权根高度排序，授权来源高度越低，权威性越高；当多签来源混合多个高度时，取签署者中最低的授权根高度。

## Rationale（理由）

- conception 已承认全网通告是中心化协作机制，需要客户端侧信任锚。
- 使用链上通告轮换可留下可审计历史。
- 多签门槛保证单一根公钥泄露不足以独立改写授权状态。
- 链上回放保留完整审计轨迹，与展示层信任链的定位一致。
- 将授权判断限制在展示层，避免影响共识规则。

## Consequences（影响）

- 客户端需要维护授权公钥状态、授权根集合和撤销状态。
- 授权根私钥应由项目方采用多人独立保管（推荐硬件密钥），并定期通过 `Rotate` 通告演练轮换流程。
- 演化通告本身需使用与普通 Proof 相同的链上发布机制；客户端在确认 29 块之前不应将其纳入授权状态。
- 通告正文格式可后续细化，但不得把通告扩展为自动执行机制。

## Conception Relationship（与构想关系）

- 补充 `conception/2.共识-端点约定.md` 中“全网通告”机制的授权生命周期。
- 不改变全网通告仅传递文本、禁止功能扩展的 conception 限制。
- 不改变其客户端展示层定位，不引入任何链上共识规则。

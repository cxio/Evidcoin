# DEC-0501: Script Bytecode Encoding（脚本字节码编码）

Status: Proposed

## Context（背景）

Conception 明确脚本由 1 字节 opcode、附参和关联数据构成，并定义源码显示约定。但附参编码、多附参顺序、关联数据长度、源码字面量歧义和参数消费顺序仍需冻结。

## Decision（决策）

建议字节码规则：

- 每条指令以 `opcode byte` 开始。
- 固定宽度附参按 DEC-0001 的大端序编码。
- 变长附参按 DEC-0001 的规范 varint 编码。
- 多个附参按文档声明顺序连续编码，不插入分隔符。
- 关联数据按指令自己的附参长度读取，不额外添加长度前缀。
- 解析器必须拒绝尾随不可达字节、截断附参和超长关联数据。

建议参数消费顺序：

- 实参区为 FIFO 队列。
- 数据栈弹出为 LIFO。
- 指令需要多个实参时，按文档参数列表从左到右绑定。
- 若从数据栈取多个实参，最后压栈的值绑定到最右侧参数。
- 多返回值按文档返回列表从左到右压入目标区域。

建议源码编译：

- 源码只是显示和编译入口，不参与链上共识。
- `Byte` 与 `Rune` 字面量冲突在冻结前不得作为共识测试向量。
- 文本别名必须编译为唯一 opcode 和附参，不得保留名称。

## Rationale（理由）

字节码解析必须唯一，否则同一脚本可能拥有多个编码。参数消费顺序会影响几乎所有脚本执行结果，应在实现前冻结。

## Consequences（影响）

- 脚本 hash、交易 hash 和脚本成本均基于字节码而非源码。
- 任何禁用指令仍可有 opcode 定义，但静态验证必须拒绝其在禁用上下文中出现。
- `CALL` 等半确定性参数数量指令需要额外静态分析规则。

- `BigInt` 正负数字节编码。
- `CALL` 禁用解除后，半确定性参数数量如何做静态成本估计。

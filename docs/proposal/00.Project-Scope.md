## 概述

本章是 `docs/proposal/`（提案层 / 技术规格层）的总入口，定义本层的定位、章节组织、全局索引与对照表，并汇总跨章的「待决问题」与实现边界。

### 文档结构定位（两层结构）

依据最新的 `docs/AGENTS.md`，Evidcoin 文档的正式结构收敛为**两层**：

| 层级 | 目录 | 角色 |
|------|------|------|
| Conception（构想层） | `conception/` | 作者原始设计思想（唯一权威来源之一） |
| Decision（决策层） | `decision/` | 补充 conception 未直接固定的规范化细节（DEC-NNNN） |

本提案层（`proposal/`）**不是**正式结构中的独立一层，而是**由 `conception/` 与 `decision/` 重新生成的可实施技术规格**——它将构想与决策逐条整理、对齐、去歧义，形成可被 Plan 与代码直接引用的工程蓝本。

> **注（措辞更新）：** 旧版 proposal（2026-05-03）按已废弃的"三层体系（Conception→Proposal→Plan）"组织。本次重写已删除该措辞。proposal 现定位为"由 conception+decision 重生的可实施规格"，其权威性永远低于 conception 与 decision；遇冲突以 conception 为准（见下文追溯规则）。

### 追溯与冲突处理规则（全局适用）

1. 每条关键规格就近标注来源（conception 文件名 / DEC-NNNN）。
2. conception 与 decision **冲突**时，正文采用 conception 口径，并加注「注：DEC-NNNN 原述 X，与 conception <文件> 冲突，本提案以 conception 为准」。
3. 仅 decision 覆盖的细节 → 正常采用并标注 DEC 编号。
4. 二者均未覆盖 → 不臆造，写入对应章「待决问题」并在本章汇总。

## 边界与限制

### 非目标 / 实现边界（C-10 落地）

以下内容 conception 已明确外包或未抽象，本提案**不强行规格化**，仅声明边界：

1. **P2P 线格式与节点发现 / 组网分享**：归由外部库实现（基网、`cxio/p2p` 等），本项目仅设计合理的接口。区块/交易及附件的传输线格式不在本提案范围内（呼应第 15 章服务边界）。
2. **版本分叉治理**：协议版本演进的治理流程（如禁用指令的统一激活方式）未由 conception 固定，列入待决（见第 10 章 C-7），不臆造治理机制。
3. **通用子链派生协议**：conception `examples/选举子链.md` 仅为方案示例，通用子链派生协议未抽象，本提案不规格化。
4. **长期存储**：区块/交易及附件数据的长期存储由外部第三方公共服务提供（数据驿站 Depots / 区块查询 Blockqs），见第 15 章。

### 本提案的稳定性边界

- 凡标注「待决」者，Plan 与代码**不得**据此实现；须待 conception/decision 补全后回填。
- 凡正文给出明确字节/字段/常量者，均可追溯至 conception 文件或 DEC 编号，Plan 可直接引用。

本章为全局索引，自身无独立待决问题；全局待决问题汇总见上文「全局待决问题汇总」表（C-6~C-10）。

## 对 Plan 的约束

1. Plan 阶段划分须与本章章节索引的「对应层/包」列对齐（Layer 0→5）。
2. 任何实现必须可追溯至某一章的某条规格；无来源标注的规格不得进入实现。
3. 待决问题（C-6~C-10）在被解决前，相关 Plan 任务应阻塞或标注为占位。
4. 实现边界（非目标）中的外包项不得在本仓库内自行实现线格式或治理协议。

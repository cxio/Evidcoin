## 概述（Overview）

Evidcoin（证信链）是一个基于区块链的通用信用载体系统，以三类凭证单元承载信用：

- **Coin（币金）**：可分割的货币单元。
- **Credit（凭信）**：不可分割的证书/合约单元。
- **Proof（存证）**：不可转让的存证单元。

系统采用历史证明（PoH，Proof-of-History）共识——铸币权来源于历史交易 ID，而非算力或财富——并全面采用后量子密码学（签名算法 ML-DSA-65）。本系统以 Go 语言实现，目前处于预实施阶段（仅文档，无生产代码）。

本篇在提案层中处于**全局索引层**：它不规格化任何具体协议字段，而是界定整个 proposal 的定位、组织方式、章节边界与全局待决事项，为后续各篇（01~15）与 Instruction 子目录提供统一入口。

### 文档定位（Document Positioning）

Evidcoin 文档的**正式结构为两层**（见 `docs/AGENTS.md`）：

| 层级 | 目录 | 作者 | 内容 |
|------|------|------|------|
| Conception（构想层） | `conception/` | 人工编写 | 协议、系统与应用边界的原始设计思想（权威上游依据） |
| Decision（决策层） | `decision/` | AI 生成 | 补充 conception 尚未直接固定的规范化细节（字节编码、哈希域隔离、边界、字段宽度、实现路径） |

**proposal（本层）与 plan 并非正式结构层级**，而是从上述两层正式结构**派生的工作产物**：

- 本提案是**由 `conception/` + `decision/` 重新生成的可实施技术规格**，目的是将分散在构想与决策中的规则整合为完整、自洽、可被 Plan 与代码直接引用的单一规格集合。
- 提案不创造新规则：每条关键规格都可追溯到某个 conception 文件或某条 DEC；二者冲突时**以 conception 为准并加注**；二者均未覆盖的缺口**只列为待决问题，绝不臆造**。
- 后续实施 plan 应可追溯到本提案及其上游 conception/decision。

> 说明：旧版文档曾使用「三层体系（Conception→Proposal→Plan 为正式结构）」的措辞，该措辞已废弃。本提案的权威上游始终是 conception 与 decision 两层；proposal/plan 仅为其派生工作产物。

### 章节组织原则（Organization Principle）

各章按**实现分层（Layer 0→5）**组织，与 decision 编号空间、代码包、Plan 阶段四方对齐：

```
Layer 5 集成/服务层:  15（公共服务接口）
Layer 4 共识层:       11~14（PoH / 端点分叉 / 组队校验 / 激励）
Layer 3 脚本层:       10 + Instruction/*（栈式虚拟机，约 254 个码位；最高码值 254/255 为系统保留，不计入指令集）
Layer 2 状态层:       09（UTXO/UTCO 状态）
Layer 1 核心层:       05~08（区块链 / 交易 / 信元 / 签名见证）
Layer 0 基础层:       01~04（类型编码 / 密码学 / 标识常量 / 哈希树）
```

每篇均采用统一六节模板：**来源追溯 / 概述 / 规格正文 / 边界与限制 / 待决问题 / 对 Plan 的约束**。

## 边界与限制（Boundaries / Non-Goals）

本提案明确**不**规格化以下内容，它们由外部实现承担或留待后续抽象：

1. **P2P 线格式（wire format）与节点发现/组网**：节点发现、连网与分享由外部库实现（如 `cxio/p2p` 等）；本提案仅在第 15 章界定合理的服务接口边界，**不定义 P2P 线格式与传输层协议**。来源：`conception/3.公共服务.md`（外包声明）、设计文档第 6 节 C-10。
2. **版本与软/硬分叉治理机制**：本提案不定义协议版本协商、软分叉/硬分叉的激活与治理流程。来源：设计文档第 6 节 C-10。
3. **通用子链派生协议**：conception 未对通用子链派生作出抽象，本提案**不强行规格化**该机制。来源：设计文档第 6 节 C-10。
4. **不写 Go 代码**：本任务仅产出 Markdown 技术规格文档，不含任何生产代码或代码骨架。
5. **不选定第三方库最终版本**：除已由 DEC 固定的实现路径（如 DEC-0104 锁定 ML-DSA-65 采用 `cloudflare/circl`，详见第 02、08 章并附取舍说明与待决项）外，本提案不冻结第三方依赖的最终选型与版本号。

此外，本提案对**禁用指令的解除方式**与**脚本成本数值**等仅作框架界定，不给出最终数值（见下文「待决问题」）。

## 待决问题（全局汇总）

本节汇总设计文档（`2026-05-29-proposal-rewrite-design.md`）第 6 节 C 类（conception 与 decision 二者均未覆盖的缺口），作为全局待决问题清单。每项注明详细讨论的承载章节；各章「待决问题」节为本汇总的细化，二者应保持一致。

1. **脚本成本数值（Script cost values）**
   - 缺口：DEC-0504 明确开放——每 opcode 的 `base_cost`、正则/随机等操作的最坏情况上界、以及三层成本上限的具体数值尚未确定。
   - 承载章节：**第 10 章（Script-System）**「待决问题」。
   - 上游：DEC-0504、设计文档 C-6。

2. **禁用指令解除方式（Disabled-opcode activation）**
   - 缺口：DEC-0505 开放——前期禁用的指令应采用「逐项 opcode 激活」还是「统一版本激活」尚未裁定。
   - 承载章节：**第 10 章（Script-System）**「待决问题」。
   - 上游：DEC-0505、设计文档 C-7。

3. **单位体系混用（Unit system: chx / Bi / 毫币）**
   - 缺口：`chx`、`Bi`、毫币等单位在 conception/decision 中未集中定义，存在混用，需统一口径。
   - 承载章节：**第 01 章（Types-And-Encoding）** 承载统一口径建议，第 03 章引用而不重复。
   - 上游：设计文档 C-8。

4. **创世具体参数（Genesis parameters）**
   - 缺口：创世时间戳、mainnet Genesis-ID 等为占位值，尚未最终确定。
   - 承载章节：**第 05 章（Blockchain-Core）** 与 **第 11 章（PoH-Consensus）** 协调承载（避免重复）。
   - 上游：设计文档 C-9。

5. **P2P 线格式 / 版本分叉治理 / 通用子链派生协议**
   - 缺口：conception 将其外包或未作抽象，本提案不强行规格化。
   - 承载章节：**本章（00）**「边界与限制」声明；第 15 章呼应 P2P 外包边界。
   - 上游：设计文档 C-10。

> 与本汇总的对应关系：第 1、2 项落在第 10 章；第 3 项落在第 01 章（第 03 章引用）；第 4 项落在第 05/11 章；第 5 项落在本章与第 15 章。

## 对 Plan 的约束（Constraints on Plan）

1. **可追溯性**：后续实施 Plan 的每个任务必须可追溯到本提案的具体章节，并经由该章节回溯到对应的 conception 文件或 DEC 编号。Plan 不得引入未在提案中固化的规则。
2. **不得绕过提案**：对于本提案标注为「待决」的事项（脚本成本数值、禁用解除方式、单位口径、创世参数、P2P/治理/子链边界），Plan **不得自行臆造实现**；须先在 conception/decision 层裁决并回写提案，再据以实施。
3. **索引一致性**：当章节文件名或划分调整时，必须同步更新本章「章节索引表」与「对照表」，保持索引与实际文件一致。
4. **边界遵守**：Plan 不得将本章「边界与限制」声明为非目标的内容（P2P 线格式、分叉治理、通用子链派生协议）纳入本项目实现范围。

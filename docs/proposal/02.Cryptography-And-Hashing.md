# Cryptography And Hashing（密码学与哈希）

## 来源追溯（Provenance）

本篇规格化 Evidcoin 的密码学原语配置：哈希算法的用途分配（algorithm profile）、域隔离标签（domain tag）、公钥哈希与地址文本编码、后量子签名算法 ML-DSA-65 的实现 profile，以及量子安全强度的取舍依据。对应代码层 `pkg/crypto`（Layer 0 基础层）。其依据为：

- **Conception 来源**：
  - `docs/conception/blockchain.md`（§哈希策略 / §附：公钥哈希的量子安全强度）：各用途的哈希算法分配表（区块头、CheckRoot、树枝/树叶、交易头、附件指纹、公钥哈希、UTXO/UTCO 叶、铸凭哈希），以及账户地址 128 位 / 其余 192 位的量子强度讨论。
  - `docs/conception/附.交易.md`（§单签名 / §多重签名 / §多重签名的地址 / §附：公钥哈希的地址编码）：单签与多签（复合）公钥哈希算法、多签初级哈希字典序排序与 `m/N` 前置、地址文本编码与 4 字节校验码流程。
  - `docs/conception/5.信用结构.md`（§关于附件）：附件完整指纹（`SHA3-512`）与附件片组哈希树（`BLAKE3-256`、叶含 2 字节序号、无域标签）。

## 概述（Overview）

本篇处于 Layer 0 基础层，紧邻第 01 章（Types-And-Encoding），共同构成全协议的哈希与签名地基。任何参与共识的字节前像（区块头、交易头、CheckRoot、树枝/树叶、UTXO/UTCO 叶、铸凭哈希、签名消息、公钥哈希）都必须：

1. 采用本篇第 3 节指定的算法 profile；
2. 在前像首段前置本篇第 1、2 节定义的域标签（附件片组哈希树为**唯一例外**，见第 4 节）；
3. 整数与字节序列的编码遵循第 01 章规则。

三者任一不一致都会导致同一逻辑数据产生不同的摘要，破坏跨实现的共识一致性。

**依赖关系**：本篇依赖第 01 章（编码规则）；被 04（哈希树）、05（区块头/CheckRoot）、06（交易头/MintPKHash）、08（签名消息/见证/ML-DSA）、09（UTXO/UTCO 叶与空根）、11（铸凭哈希）、14（Coinbase 输出地址）等所有涉及哈希或签名的上层引用。第 01 章第 8 节（地址编码）已作指针引向本篇第 5 节。

## 规格正文（Specification）

### 1. 域标签编码（Domain Tag Encoding）

为防止不同结构的相同字节前像产生跨用途混淆，所有链上共识哈希前像首段必须前置**域标签**（domain tag）。（依据 DEC-0002 §域标签编码）

- 域标签编码为 ASCII 字符串常量：`"Evidcoin/v1/" || name || 0x00`。其中 `name` 为下表第 2 节中的用途名（如 `block.header`），尾部 `0x00` 为分隔符。（依据 DEC-0002）
- 域标签**作为 ASCII 字符串常量直接进入哈希前像**，不压缩为整数编号。（依据 DEC-0002）
- 域标签**必须作为哈希前像首段**，不参与用户可控字段的长度解释（即标签长度固定、不写长度前缀）。（依据 DEC-0002）
- **同一算法不同用途必须使用不同标签**，即使输入结构当前不可混淆。（依据 DEC-0002）
- **版本号 `v1` 位于标签头部**，用于未来协议升级时整体替换；当前所有标签均使用 `v1`。后续整体迁移到 `Evidcoin/v2/...` 时，所有用途的域标签同步更换版本号，实现版本间的整体名字空间隔离。（依据 DEC-0002 §域标签编码 / §Rationale）

哈希前像的一般形态：

```text
preimage = DomainTag(name) || payload
         = "Evidcoin/v1/" || name || 0x00 || payload
digest   = <profile-algorithm>(preimage)
```

> 说明：尾部 `0x00` 分隔符可避免标签名与后续 `payload` 字段拼接时的歧义（如 `tree.leaf` 与 `tree.leaf...` 前缀混淆）。（依据 DEC-0002 §Rationale）

### 3. 算法 profile 表（Hash Algorithm Profile）

各用途的哈希算法分配如下，与 conception `blockchain.md#哈希策略` 完全一致，由 DEC-0002 冻结。（依据 conception blockchain.md §哈希策略；DEC-0002 §算法 profile）

| 用途 | 算法 | 输出长度 | 域标签 | 来源 |
|------|------|----------|--------|------|
| 区块头（BlockID） | SHA3-384 | 48B | `block.header` | blockchain.md / DEC-0002 |
| 交易头（TxID） | SHA3-384 | 48B | `tx.header` | blockchain.md / DEC-0002 |
| CheckRoot（校验根） | SHA3-384 | 48B | `checkroot` | blockchain.md / DEC-0002 |
| UTXO/UTCO 末端叶 | SHA3-384 | 48B | `utxo.leaf` / `utco.leaf` | blockchain.md / DEC-0002 |
| UTXO/UTCO 空状态树根 | SHA3-384 | 48B | `utxo.empty` / `utco.empty` | DEC-0201 |
| 通用哈希树分支 | BLAKE3-256 | 32B | `tree.branch` | blockchain.md / DEC-0002 |
| 通用哈希树叶（默认） | SHA3-384 | 48B | `tree.leaf` | blockchain.md / DEC-0002 |
| 附件完整指纹 | SHA3-512 | 64B | `attachment.fingerprint` | blockchain.md / 5.信用结构.md / DEC-0002 |
| 公钥哈希（单签/多签） | SHA3-256(BLAKE2b-512(...)) | 32B | `address.single` / `address.multi` | blockchain.md / 附.交易.md / DEC-0002 |
| 铸凭哈希 | BLAKE3-256 | 32B | `mint.hash` | blockchain.md / DEC-0002 |

设计取舍要点（依据 conception blockchain.md §哈希策略）：

- **SHA3-384（48B）** 用于区块头、交易头、CheckRoot、UTXO/UTCO 叶：兼顾量子安全（192 位级别）与数据量。CheckRoot 为一次性合并开销，成本可控。
- **BLAKE3-256（32B）** 用于通用树分支与铸凭哈希：树结构需处理大量多哈希场景，BLAKE3 提高性能并节省内存；铸凭哈希在可能有大量参与者的竞争场景下关注速度与效率。
- **树叶子默认采用 SHA3-384**，与树枝段（BLAKE3-256）采用**不同算法**（除非另有说明，如附件片组树例外）。
- **附件完整指纹 SHA3-512（64B）**：确保超长期安全，与附件片组哈希（BLAKE3-256）形成双哈希耦合保护。
- **公钥哈希 SHA3-256(BLAKE2b-512(...))（32B）**：适量节省空间，量子强度取舍见第 7 节。

**BLAKE3 模式约束**：BLAKE3 **一律使用普通 hash 模式，不使用 keyed mode**，所有用途统一为普通 hash 加域标签前缀（附件片组树例外，见第 4 节）。这意味着同一字节序列在任意上下文产生相同摘要，跨用途隔离**完全依赖域标签**。（依据 DEC-0002 §算法 profile / §Consequences）

### 4. 附件片组哈希树的域标签例外（Attachment Piece-Set Tree Exception）

附件片组哈希树（attachment piece-set hash tree）是全局"哈希前像首段必须为域标签"规则的**唯一例外**：其叶子节点与分支节点皆为 `BLAKE3-256` 且**不前置任何域标签**。理由是该哈希树面向通用文件分享场景，便于与外部数据网络（P2P 文件分片验证工具）互操作，使链外节点可直接复用普通文件分片验证流程，不必依赖本协议域标签规范。（依据 DEC-0002 §附件片组哈希树的例外；conception 5.信用结构.md §关于附件）

- **叶子节点**：`BLAKE3-256(2-byte seq || BLAKE3-256(piece_data))`。即 34 字节预像中，前 2 字节为分片顺序号（big-endian），后 32 字节为该分片数据的 `BLAKE3-256` 哈希。（依据 DEC-0002；conception 5.信用结构.md「片组哈希树的叶子节点为各分片数据的哈希（32字节），另外前置2字节序号，共34字节」）
- **分支节点**：`BLAKE3-256(left || right)`。（依据 DEC-0002）
- 在分片数据哈希前置 2 字节序号的动作由**验证者**实施，源节点无法据此作弊。（依据 conception 5.信用结构.md §附件的分片验证）

> 说明：附件片组哈希值与协议内其它树根虽算法相同（BLAKE3-256），但因前像无域标签而属于不同名字空间，二者不会混淆。（依据 DEC-0002 §Consequences）附件 ID 的整体结构（类型、指纹、分片数量、片组哈希、大小）属信元规格，详见第 07 章（Coin-Credit-Proof-Units）；片组哈希树的二元结合与含序结构详见第 04 章（Hash-Trees）。本节仅固定其算法 profile 与"无域标签"例外。

### 5. 公钥哈希与地址编码（Public-Key Hash and Address Encoding）

本节承载账户地址的**完整文本编码规格**（第 01 章第 8 节已作指针引向本节）。

#### 5.1 公钥哈希（Public-Key Hash）

公钥哈希输出固定 32 字节，单签与复合（多签）外观无区别（隐私安全），但派生逻辑不同。（依据 conception 附.交易.md §单签名 / §多重签名）

- **单签公钥哈希**：`PKHash = SHA3-256(BLAKE2b-512(pubKeyBytes))`。域标签 `address.single`。（依据 conception 附.交易.md「单公钥哈希的算法：SHA3-256( BLAKE2b-512(pubKey) )」；DEC-0104 §公钥哈希；DEC-0002）
- **多签复合公钥哈希**（M-of-N）：（依据 conception 附.交易.md §多重签名的地址；DEC-0104 §公钥哈希；DEC-0002，域标签 `address.multi`）
  1. 对 N 个公钥分别计算**初级哈希** `BaseH_i = BLAKE3-256(pubKeyBytes_i)`。
  2. 将 N 个初级哈希**按字典序排序并串联**：`BaseHAll = Concat(Sort(BaseH_1, ..., BaseH_N))`。
  3. 前置 `m || n` 两字节配比（各 1 字节），计算复合公钥哈希：`PKHmix = SHA3-256(BLAKE2b-512(m || n || BaseHAll))`。

  约束：
  - `m`、`n` 两值**均不得为 0**，且 `m <= n`；`m/n` 最大支持 `255/255`。（依据 conception 附.交易.md「`m` 和 `N` 任一值不得为零」「`m/N` 配比为 1+1 两个字节，最多支持 255/255」；DEC-0104「`m` 和 `n` 均不得为 0，且 `m <= n`」）
  - **不得包含重复公钥**；出现重复公钥时地址构造与见证验证均**非法**。（依据 DEC-0104 §公钥哈希 / §Confirmation）

> 注：先对各公钥计算 `BLAKE3-256` 初级哈希再排序串联，可保护公钥隐私并稳定地址生成。（依据 DEC-0104 §Rationale；conception 附.交易.md）多签见证容器中"提供顺序"与签名消息排序等其它两套排序规则属第 08 章，本节仅定义**地址派生时的初级哈希字典序排序**。

#### 5.2 地址文本编码（Address Text Encoding）

地址将 32 字节公钥哈希编码为可读文本，附带 4 字节校验码与网络识别前缀。（依据 conception 附.交易.md §附：公钥哈希的地址编码；DEC-0104 §地址规则）

地址文本格式：

```text
address  = prefix || Base58(pubKeyHash || checksum)
checksum = last4( SHA2-256( SHA2-256( prefix || pubKeyHash ) ) )
```

- **Base58 字母表**：Bitcoin 字母表。（依据 DEC-0104）
- **`prefix`（网络前缀）参与校验码计算，但不进入 Base58 负载**。即校验码的哈希前像包含 `prefix`，而 Base58 编码的对象只有 `pubKeyHash || checksum`。（依据 DEC-0104；conception 附.交易.md §编码：校验码哈希时含前缀，Base58 文本序列编码时无前缀，最后附上前缀）
- **校验码算法为 `SHA2-256`，执行 2 次（double SHA-256），取末尾 4 字节**。（依据 conception 附.交易.md §编码 / §校验；DEC-0104）
- **网络前缀**：主网、测试网、开发网必须使用不同前缀，分别为：（依据 DEC-0104）

  | 网络 | prefix |
  |------|--------|
  | 主网（mainnet） | `Cx` |
  | 测试网（testnet） | `Tx` |
  | 开发网（devnet） | `Dx` |

编码流程（依据 conception 附.交易.md §编码）：

0. 公钥哈希前置识别前缀，得 `prefix || pubKeyHash`。
1. 对其执行 2 次 `SHA2-256`，取末尾 4 字节为校验码 `checksum`。
2. 在公钥哈希之后附上校验码（**此时不含前缀**），Base58 编码为文本序列。
3. 文本序列前附上识别前缀，即得地址。

校验流程（依据 conception 附.交易.md §校验）：

0. 提取前缀与文本序列。
1. Base58 解码文本序列为字节序列，截取末尾 4 字节为校验码，前段为公钥哈希。
2. 对 `prefix || pubKeyHash` 执行 2 次 `SHA2-256`，取末尾 4 字节为重算校验码。
3. 比较两个校验码，相同则通过。

> 注：`prefix` 变更会导致校验码变化；不同网络的地址不能混用。（依据 DEC-0104 §Consequences）

### 6. ML-DSA-65 签名算法 profile（ML-DSA-65 Signature Profile）

Evidcoin 采用后量子签名算法 ML-DSA-65（FIPS 204）。本节仅冻结**算法 profile 与字节编码**；签名消息的字节布局（ChainScope / SigScope / TxHeaderCore / Covered* 等）属第 08 章（Signatures-And-Witness），本节给指针。

- **固定使用 ML-DSA-65**。（依据 DEC-0104 §ML-DSA 规则；conception blockchain.md §哈希策略「抗量子签名算法」）
- **固定使用 `github.com/cloudflare/circl` 的 ML-DSA-65 实现 profile**。（依据 DEC-0104）
- **公钥、私钥与签名的序列化采用 `circl` 的 canonical byte encoding**。跨实现必须产出字节级一致的编码。（依据 DEC-0104）
- **签名验证输入为签名消息字节序列**（DEC-0102 定义、详细布局见第 08 章）。本节不展开签名消息布局，仅确认其作为 ML-DSA-65 验证的待签消息。（依据 DEC-0104 §ML-DSA 规则）

> 注（实现取舍）：根 `AGENTS.md` 建议"优先用标准库"（Go 1.25+ 可能内置 ML-DSA）。本提案**以 DEC-0104 为准，固定 `github.com/cloudflare/circl` 的 ML-DSA-65 profile**——因为 DEC-0104 更具体，且关乎公钥/私钥/签名的 canonical byte encoding 跨实现一致性（若 Go 标准库与第三方库的 ML-DSA 编码不一致，必须在实现前冻结一种 profile，见 DEC-0104 §Consequences）。是否随 Go 标准库 ML-DSA 成熟而改用，登记为待决（参见「待决问题」OQ-02-2）。

### 7. 量子安全强度（Quantum Security Strength）

哈希算法选择的安全强度依据如下（依据 conception blockchain.md §附：公钥哈希的量子安全强度）：

- **账户地址（公钥哈希）采用 `SHA3-256(BLAKE2b-512(...))`，输出 32 字节，提供约 128 位量子安全强度**（SHA3-256 在 Grover 攻击下的下限）。
- **系统中其它大多数哈希采用 SHA3-384，提供 192 位量子安全强度**。
- 账户地址生命周期与 UTXO 绑定，未被花费的地址会持续暴露在链上，是量子计算机成熟后系统中**最先受压力**的哈希环节。
- 地址采用 32B（vs 48B）是**空间节省与安全性之间的有意权衡**，辅以抗量子签名算法 ML-DSA-65，风险可接受。

> 说明：长期历史安全由哈希约束保证（签名数据后期可剪枝）；区块头/交易头/CheckRoot 等共识根采用 SHA3-384 的 192 位强度，是全链长期安全的主基线。（依据 conception blockchain.md §哈希策略）

## 边界与限制（Boundaries / Non-Goals）

1. **域标签为前像首段、不可省略**：除附件片组哈希树（第 4 节）这一唯一例外外，所有链上共识哈希前像必须以域标签开头；任何冻结后的哈希前像都须列明其域标签。（DEC-0002 §Consequences）
2. **BLAKE3 不用 keyed mode**：跨用途隔离完全依赖域标签，实现不得用 keyed mode 代替域标签隔离。
3. **不规格化哈希树结构**：奇偶层提升、单叶树根、验证路径编码、各专用树（区块交易树、输入/输出树、UTXO/UTCO 宽成员树）的层级与组织属第 04 章；本篇仅定算法 profile 与域标签。
4. **不规格化状态树细节**：UTXO/UTCO 的年度/TxID 分层、空年度空分组处理、过期处理属第 09 章；本篇仅确认 `utxo.empty` / `utco.empty` 域标签归属。
5. **不规格化签名消息布局与见证容器**：授权种类、签名消息字段顺序、见证容器剪枝、Coinbase 签名消息属第 08 章；本篇仅定 ML-DSA-65 algorithm profile 与公钥/签名编码。
6. **不臆造未冻结参数**：域标签全集为闭集（14 项）；新增用途须经 DEC 显式声明并同步本表与 DEC-0002 清单。

## 对 Plan 的约束（Constraints on Plan）

1. **统一哈希与域标签实现**：`pkg/crypto` 必须提供唯一的域标签构造（`DomainTag(name) = "Evidcoin/v1/" || name || 0x00`）与各 profile 哈希封装（SHA3-384 / BLAKE3-256 / SHA3-512 / SHA3-256(BLAKE2b-512) / SHA2-256），所有上层哈希均经由它，不得各自拼接前像。
2. **域标签闭集**：实现仅允许第 2 节 14 项域标签；新增用途须先回写 DEC（并补 DEC-0002 清单）与本篇第 2 节，再实现。`utxo.empty` / `utco.empty` 在 DEC-0002 回写前以本篇第 2 节为权威（OQ-02-1）。
3. **附件片组树无域标签**：附件片组哈希树的实现路径必须与其它链上哈希分离——叶 `BLAKE3-256(2B seq || BLAKE3-256(piece))`、枝 `BLAKE3-256(left||right)`，**不得**前置域标签；并提供与外部通用文件分片验证互操作的测试向量。
4. **BLAKE3 普通模式**：实现一律使用 BLAKE3 普通 hash 模式，禁止 keyed mode；跨用途隔离仅靠域标签。
5. **地址编解码与校验**：`pkg/crypto`（或地址子包）必须实现单签/多签公钥哈希派生、地址 Base58 编解码、双 SHA2-256 校验码，并强制：多签 `m,n != 0 && m <= n`、初级哈希字典序排序、禁止重复公钥、`prefix` 参与校验码但不入 Base58 负载、三网前缀（`Cx`/`Tx`/`Dx`）隔离。须随附各网络的地址编解码与校验失败测试向量。
6. **ML-DSA-65 单一 profile**：实现固定 ML-DSA-65 + `cloudflare/circl` profile 与 canonical byte encoding（OQ-02-2 裁决前不得混入标准库编码）；签名消息布局引用第 08 章。须冻结公钥/私钥/签名的字节级测试向量。
7. **追溯硬约束**：所有哈希前像（域标签 + payload 顺序）须可追溯至本篇第 2、3 节与对应 DEC；任何前像变更须先回写本篇与 DEC，再改实现。

# 架构决策（未决项）

> **注**：评审基于 Claude Opus 4.6。

## Critical 层级

- C-1 铸凭哈希内层哈希算法：
    - BLAKE3-256
    - 内容为确定性数据，只是计算确定性摘要。因此无安全性问题。
    - 可能有大量铸凭资格提交，因此效率很重要。

- C-2 铸凭哈希计算中的 X 计算：
    - 时间戳为毫秒：粒度更细，也是脚本系统中时间戳默认单位，统一观感。
    - 大整数乘法：不损失精度。
    - 大端序编码。

- C-3 varint编码：
    - LEB128（Protocol Buffers）。

- C-4 domain tag 哈希标识前缀:
    - "Evidcoin:" + Purpose + ":v" + version-number + "\x00"
    - version-number 为变长整数。

## High 层级

- H-1 Float 的确定性：
    - 采用 IEEE 754 binary64 round-to-nearest-even，且所有 NaN 统一为 quiet NaN。

- H-2 脚本PASS初始状态：
    - 确定为 true。
    - 如果脚本中没有 CHECK/PASS，默认通过。即：只有设置关卡，才可能阻止。

- H-3 CHECK 覆盖语义：
    - 按检查结果任意覆盖：false -> true; true -> false 皆可。即最终态决定最终结果。

- H-4 UTXO/UTCO 指纹树中间层的TxID索引：
    - 0-based，遵循通常习惯。

- H-5 奖励取整余数归属：
    - 按 "40% >> 10% >> 20% >> 20% >> 10%" 顺序计算：
    - 前面4项（除最后一项）都是向下取整。
    - 末尾一项为减法（总数 - 前4项之和）。

- H-6 Coinbase HashInputs:
    - BLAKE3-256( "Evidcoin:Coinbase:v1" + 区块高度 )

- H-7 相同铸凭哈希决胜：
    - 相同铸凭哈希视为同一个主体，没有区分。
    - 如果真的不同交易ID参与计算的铸凭哈希相同，那就按“先到先得”的逻辑执行（不接受相同铸凭哈希的第二个申请）。
    - 哈希结果本身就是唯一性原则。哈希已足够长，没必要增加复杂性。

## Medium 层级

- M-1 哈希树空根/单叶/奇数叶策略：
    - 空树 = 全零 Hash；单叶 = 叶子 Hash 本身；奇数叶 = 不复制最后一个叶子，直接提升到下一层。

- M-2 MaxStackHeight 终点问题（off-by-one）：
    - 构想层为小于（<）限制时，<= 上限值统一把数字-1，严格遵循构想设定的上限值。

- M-3 同区块未确认交易的前向（链式）消费：
    - 明确禁止。
    - 不然影响组队校验的任务分派（无限依赖——逻辑上），会被利用构造为长依赖攻击。

- M-4 输入项TxID 20字节碰撞可能性：
    - 顶层有确定性的年度分区，单年度内交易规模成长有限，20字节足够抵御碰撞。且遇碰撞歧义会拒绝，不影响安全，只影响用户体验（但几乎不可能发生）。
    - 简化处理完全可行，没必要为不可能发生的用户体验变差增加复杂性。

- M-5 公共服务的评估问题：
    - 很难设计。
    - Blockqs 的查询可用性证明如何设计？真的能有效抑制作弊吗？
    - Depots 的数据存储证明虽然可以通过分片哈希的序数抽查，但依然能发展出作弊手段。
    - 就项目的初期来说，这样的复杂性不值得。

- M-6 ML-DSA-65 集成路径问题：
    - 按行业最佳实践做法执行，AI Agent 可自行斟酌决定（告知用户确认即可）。

- M-7 区块签名消息范围：
    - 确定签名 CheckRoot 字段。理由如下：
    - 相比于管理层，拥有铸凭交易的铸造者更普通，更不专业。
    - 区块头字段固定，无法作弊（否则其它节点不会接受该区块，管理层自身损失）。
    - 作为轻量上线的铸造参与者（比如围观者），其实无法验证交易集的内容（比如区块头内的币权销毁字段值）。因此签名约束至区块头没有意义。
    - 所有不参与哈希计算的签名都可以被最终移除，区块链的长期安全性不依赖签名。签名只负责末端一定长度区块链的实时安全性，因为超过限度的分叉将成为一条与己无关的支链。注：这利用的是末端实时性社会共识。
    注意：区块头哈希包含 CheckRoot，但不包含对它的签名数据。

- M-8 SYS_NULL 的解锁段使用例外：
    - 首先该指令在逻辑上应当归属于系统级，所以被划归到系统指令区间。
    - 在解锁段标记 NULL 点十分有意义，属于重要功能。比如灵活提取解锁段指令序列，用于验证综合性的脚本输入。
    - 这是解锁段超范围指令码唯一的例外。因为基础指令集已基本完备，考虑周全，很难再有其它的例外了。
    - 指令码按类型划归，可能有意想不到的好处。如果将 SYS_NULL 例外定义到其它类别，可能更不合适。

## Low 层级

- L-2 地址文本编码前缀：
    - 字符串：Cx

## Nit（细微）

- N-2 Credit Config 低 10 位描述长度：
    - 是凭信输出项的固定配置，用于对描述的最大长度限定（如果凭信可修改，后期转移时可对描述长度进行限定）。
